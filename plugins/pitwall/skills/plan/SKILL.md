# plan - stages 4 and 5

> Status: built in T2.

Turns the idea, the discovery, the decisions and the spikes into a plan the epic loop can run: `docs/SPEC.md`, `docs/EPICS.md` and one file per epic. A `plan-reviewer` agent with a fresh context reviews it from the documents only and sets `ai-review` on the plan PR; this conversation closes the findings with the owner. Once both checks are green and the owner says yes, the plan merges into `main` with a merge commit that records the approval.

Plugin files used: `${CLAUDE_PLUGIN_ROOT}/config/defaults.json` (`processLevels`, `riskClasses`, `plan`, `planReview`, `review`, `planning.branch`) and the scripts in `${CLAUDE_PLUGIN_ROOT}/scripts/`: `docs-check.mjs`, `merge.mjs` (and `review-status.mjs`, which only the reviewer runs).

## Rules

- Run each command in the steps as written, from the project root, one command per call.
- One question per message, then wait. Never answer for the owner, never accept a risk for them, and never merge without their yes in this conversation. What you only inferred from the owner's words or the docs is not a question each: such facts go to the owner as one numbered list, to confirm as a whole or correct by number.
- Never edit `docs/PLAN-REVIEW.md` and never set `ai-review`: both belong to the reviewer. Close findings in the epics, `docs/SPEC.md`, `docs/RISKS.md` or through `/pitwall:decide`, and let the next round record them.
- Keep the template's headings and table columns exactly as they are: the docs check reads them.
- Write plain Markdown the docs check reads as GitHub shows it: headings and table rows at the first column, a blank line after every table, tables only where the template has one, fences at the first column; no HTML or comments, no block quotes, no setext headings, no link reference definitions, no invisible characters. Cells the check judges (an epic's risk, dependencies and status; a risk's ID, fallback and date) hold plain text: no links, HTML tags, strikethrough, character references or backslash escapes (a "<" before a number, one "~" in a path and a "\" in a Windows path are fine).
- When a script hands a step over, show the owner its HANDOFF lines verbatim: the commands under "Run this yourself" are for the owner, and the one under "Then run this to record the result" finishes the step afterwards. Never retry a refused write another way.

## Steps

1. **Preflight.** Read `.claude/pitwall.json`; without it, stop: run `/pitwall:kickoff` first. Run `git status --porcelain` and look at what it lists before any branch is switched: changes this skill made in an earlier run (in `docs/`) stay, anything else the owner commits or drops first. Switch to the planning branch (`planning.branch`). If `mergeProtection` is `pending`, tell the owner once and offer to run `node "${CLAUDE_PLUGIN_ROOT}/scripts/protect.mjs"`. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/docs-check.mjs" --stage decide`; if it fails, stop: finish `/pitwall:decide` first. When `docs/spikes/` holds a spike besides `README.md` and `template.md`, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/docs-check.mjs" --stage spike`; a spike that is not concluded goes back to `/pitwall:spike`, and one that is not confirmed and whose follow-up is still pending goes to `/pitwall:decide <area>` first. When the level's `spikeRequired` is true and the riskiest assumption in `docs/DISCOVERY.md` has no concluded spike, stop: run `/pitwall:spike` first.
2. **Resume.** When `node "${CLAUDE_PLUGIN_ROOT}/scripts/docs-check.mjs" --stage plan-review` already passes and `git status --porcelain` prints nothing, the plan is reviewed: go to step 11. When `docs/EPICS.md` already passes `--stage plan`: with a clean tree and the plan committed, go to step 9; otherwise the owner has not accepted it yet: go to step 7.
3. **Read.** `docs/IDEA.md`, `docs/DISCOVERY.md`, `docs/STACK.md`, every ADR in `docs/adr/`, the spikes, `docs/RISKS.md`, `CLAUDE.md`, and `docs/epics/E0-skeleton.md`.
4. **Fill `docs/SPEC.md`**, keeping its headings: Overview, the product in a paragraph; Scenarios, the scenarios of `docs/DISCOVERY.md`; Architecture, the parts and how they talk, citing the ADRs instead of repeating them; Data model, the entities and where they live, or what little there is; Non-functional requirements, one line per item of `planReview.nonFunctional` for the level, from the constraints and decisions (write `open` where nothing answers it yet).
5. **Launch questions.** Go through the items of `planReview.launch` for the level. Every item whose answer the idea and the decisions already imply goes into one message, as a numbered list of the answers you propose, each with where it comes from: the owner confirms the list as a whole or corrects items by number. Only an item that nothing answers, or that leaves a real choice, is asked on its own, one per message, with its options. Record each answer in the Launch section of `docs/SPEC.md` with today's date: `- <item>: <answer> (confirmed <date>)`.
6. **Draft the epics.**
   - E0 first, from `docs/epics/E0-skeleton.md`: fill its `ADR:` line with the stack ADRs, and fit its criteria to the level's `staging`; keep its other criteria.
   - Then E1, E2, ... in the order they will be built. One epic is one PR with a testable result; an epic that touches more modules or packages than `plan.epicSplit` allows is split. At lite, no more than `processLevels.lite.epics.max` epics after E0.
   - Each epic: a goal in one line; `Visible after it:`, one line on what the owner can see or do in the product once the epic is merged, in their words, or that nothing new shows when it changes only the inside (E0 too: what the bare skeleton shows, and that it does nothing yet); acceptance criteria `E<n>-AC<m>`, numbered from 1, written for QA, checkable without knowing the code, and together covering every scenario; `Depends on:` earlier epics only; `ADR:` the ADRs it follows, or `none`; a risk class from `riskClasses` by its `examples`; out of scope; open questions.
   - Cite a high-risk assumption `A-n` in the criterion that settles it.
7. **Show the plan** in one message: a table (Epic, Goal, Visible after it, Risk, Depends on) and the criteria of each epic. The owner accepts it or names changes; apply them and show the changed epics again until the owner accepts.
8. **Write and commit.** Write `docs/EPICS.md` (one row per epic, its ID linked to its file the way the E0 row is, status `planned`) and one file per epic in `docs/epics/`, from `E0-skeleton.md`. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/docs-check.mjs" --stage plan`; fix what it reports and run it again until it passes. Then `git add docs/ .claude/pitwall.json` and `git commit -m "docs: plan"`. With a remote: `git push -u origin <branch>`, then `gh pr list --head <branch> --state open`, and when it lists nothing, `gh pr create --base main --head <branch> --title "Plan: <project name>" --body "Stages 1 to 5: discovery, decisions, spikes, the plan and its review. It merges once gate and ai-review are green and the owner says yes."`. A failed push or PR is not retried: show the error and go on; the reviewer's status step hands it over.
9. **A review round.** Dispatch the `pitwall:plan-reviewer` agent with the brief below, a fresh agent each round. It writes `docs/PLAN-REVIEW.md`, runs `review-status.mjs` (which commits that file, pushes, and sets `ai-review`) and returns its report. Show the owner its STATUS, the open items in a short list, and any HANDOFF lines verbatim.
10. **Close the findings.** For each open item:
    - a gap in the plan (a criterion missing or not checkable, an epic too big, a wrong order): fix it in the epics or `docs/SPEC.md`;
    - a decision that turns out to be missing or wrong: the owner runs `/pitwall:decide <area>`;
    - a risk to accept: ask the owner, one per message; on yes, add the next `R-n` to `docs/RISKS.md` with the risk, the owner's fallback and today's date in "Accepted on";
    - a question only the owner can answer (the reviewer's NEEDS_OWNER): ask it, one per message, and record the answer where it belongs.
    Run `--stage plan` again, `git add docs/ .claude/pitwall.json`, `git commit -m "docs: close plan review round <n>"`, push with a remote, and go back to step 9.
    The loop has an end, set by the process level: `ownerDecidesAtReject` and `maxRounds` are the level's `planReviewRounds` in `processLevels` where it has them, and `review`'s otherwise. The first `ownerDecidesAtReject` rounds are full reviews. After them, show the owner what is still open, and they decide, item by item, to fix it or accept it as a risk. Every later round is a verification round (the brief says so): the reviewer checks that each finding it already holds is closed, adds a new finding only when it is blocking, and leaves anything smaller as a note. When a verification round still ends in CHANGES, the owner decides on what is open again, before one more verification round. Rounds stop at `maxRounds` in all: before the last one the owner fixes or accepts as a risk, item by item, whatever is open, and the last round (the brief says that, and then not that it is a verification round) only records it and adds no finding; a point it marks `BLOCKING:` in its notes, show the owner before the merge question. A last round that still does not end in APPROVED stops the review: show the owner what is open and why, and run nothing more by yourself. The limit is theirs to pass: they change the plan, or accept what is open as a risk, and ask for one more round, which is a last round again, or they put the plan aside. Only a finding of the kind `review.findings.realistic` describes blocks; one of the kind `review.findings.exotic` describes the reviewer lists once, and the owner accepts it as one risk.
    The reviewer's notes, its smaller points that block nothing, go where the level's `planReviewNotes` says. `implementers`: the reviewer writes them into `docs/PLAN-REVIEW.md` under "Notes for the implementers", and `/pitwall:continue` hands each epic's notes to its implementer. Tell the owner how many there are and where they are, and ask nothing about them: a note put into the plan after APPROVED moves the reviewed commit and costs another round. `owner`: show the owner the notes in one message; each is theirs to add to the plan or leave, and none blocks the merge.
11. **Merge**, once the reviewer returned APPROVED.
    - Show the owner one summary: the epics (ID, goal, what is visible after each, risk), the risks accepted in `docs/RISKS.md`, the reviewer's verdict, and the notes it left for the implementers, by their number. Ask one question: merge the plan into `main` now?
    - On yes, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/merge.mjs" --plan --owner-approved`. It checks that `gate` and `ai-review` are green on the approved commit, waiting up to `plan.gateWaitSeconds` for a gate that is still running, and that a merge commit is allowed, then merges with `Plan approved by the owner, <date>, at <sha>` in the message.
    - Exit 0 (`RESULT: merged`): with a remote, `git switch main` and `git pull --ff-only`. Exit 3: when the gate is still running, run it again (it waits again, and the yes still stands); otherwise show the HANDOFF block verbatim. Exit 1: show why it refused; when `ai-review` is not success on the head, run one more round (step 9), within the limit of step 10 or, past it, by the owner's word.
    - On no, or not yet: stop here; `/pitwall:plan` resumes at this step.
12. **Hand over.** Tell the owner, in a few lines: the number of epics, and for each what they will see in the product once it is merged (its `Visible after it:` line), so that a skeleton or an epic that changes only the inside does not read as a broken product when they try it; the accepted risks; whether the plan is merged (or the pending command); and that the next stage is the epic loop, which starts with E0: `/pitwall:continue`, or just "continue".

## Reviewer brief

The brief holds only what the reviewer needs to find the documents, never anything from this conversation: the project root; the round number, which survives a resume because it is one more than the commits on the planning branch whose subject starts `docs: plan review,` (`git log --oneline --grep="^docs: plan review," <branch>` lists them), from round `ownerDecidesAtReject` + 1 on, that it is a verification round, and from round `maxRounds` on, that it is the last round and not a verification round (both numbers by the level, as step 10 reads them); the process level from `.claude/pitwall.json`; where the notes go, `implementers` or `owner` (the level's `planReviewNotes`); the config path `${CLAUDE_PLUGIN_ROOT}/config/defaults.json`; the template of its file, `${CLAUDE_PLUGIN_ROOT}/template/docs/PLAN-REVIEW.md`; the paths to read (`CLAUDE.md`, `docs/IDEA.md`, `docs/DISCOVERY.md`, `docs/SPEC.md`, `docs/STACK.md`, `docs/adr/`, `docs/spikes/`, `docs/EPICS.md`, `docs/epics/`, `docs/RISKS.md`, `docs/PLAN-REVIEW.md`); and the two commands it may run, with their paths and the project root spelled out, so it needs no `cd` (pitwall's hook lets the reviewer run each one alone, or after `cd` to the project root):

- `node "${CLAUDE_PLUGIN_ROOT}/scripts/docs-check.mjs" --root "<project root>" --stage plan-review` (add `,spike` when there are spikes);
- `node "${CLAUDE_PLUGIN_ROOT}/scripts/review-status.mjs" --project "<project root>" --review plan --state success` or `--state failure`.

## Output

- `docs/SPEC.md` filled in, `docs/EPICS.md` and `docs/epics/E<n>-<slug>.md` per epic, `docs/RISKS.md` with the risks the owner accepted.
- `docs/PLAN-REVIEW.md`, written by the reviewer: pre-mortem, non-functional and launch items, epic sizing, findings, each closed.
- The plan PR from the planning branch with `ai-review` from the reviewer, merged into `main` with a merge commit after the owner's yes.

## Check

`docs-check.mjs --stage plan-review` passes (it includes `--stage plan`): every epic has acceptance criteria and a risk class, rows and files agree, ADR IDs and links resolve, dependencies point to earlier epics and form no cycle, E0 comes first; every reason and finding is closed by an ID or an accepted risk, every item of the level is answered, every epic is sized, and every high-risk assumption is covered. The owner said yes before the merge.
