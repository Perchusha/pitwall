# continue - the conductor

> Status: built in T3b; bugs by severity since T4b; releases through `/pitwall:release` since T4c (ADR-0013); the stages before the loop since T5a.

```
ORIENT -> the stage the project has reached -> "move on to the next stage?" -> ... -> the plan merged
       -> SELECT -> CLARIFY -> BRANCH -> IMPLEMENT -> GATE -> PR -> REVIEW -> MERGE -> RECORD -> loop
```

Takes a project along the whole path, so the owner never has to know which command comes next. Before the plan is merged it runs one stage at a time, each by that stage's own skill, and asks before it moves on. With a merged plan it takes the project through its changes, one at a time: the change in flight, the fix of a blocking bug, the next epic, or the fix of a bug that is not blocking. Implementers write the code, a fresh `code-reviewer` judges it, `merge.mjs` merges it by its risk class, and the owner answers what only the owner can answer.

Plugin files used: `${CLAUDE_PLUGIN_ROOT}/config/defaults.json` (`processLevels`, `planning`, `riskClasses`, `budgets`, `review`, `loop`, `mergeProtection`, `bugs`), the stage skills `${CLAUDE_PLUGIN_ROOT}/skills/<stage>/SKILL.md` (`kickoff`, `discovery`, `decide`, `spike`, `plan`) and the scripts in `${CLAUDE_PLUGIN_ROOT}/scripts/`: `bugs.mjs`, `docs-check.mjs`, `merge.mjs`, `protect.mjs`, `merge-choice.mjs`, which runs only through Claude Code's permission prompt (and `review-status.mjs`, which only the reviewer runs).

Arguments, as the owner gave them (nothing after the colon means none): $ARGUMENTS

## Rules

- Run each command as written, from the project root, one command per call.
- One question per message, then wait. Never answer for the owner, never accept a risk for them, and never pass `--owner-approved` without their yes to that merge in this conversation. What you only inferred from the owner's words or the docs is not a question each: such facts go to the owner as one numbered list, to confirm as a whole or correct by number.
- Whenever the owner is about to look at the product (a manual QA scenario, a yes to a merge they want to try first), say first what this change makes visible, from the epic's `Visible after it:` line or, without one, its goal and criteria, and what is not there yet, with the epic that brings it: an owner who tests as a user must not take a skeleton for a broken product.
- In the loop, this conversation writes docs only: the change's own file, `docs/EPICS.md`, `docs/RISKS.md`, `docs/JOURNAL.md` and the Approval section of `docs/PLAN-REVIEW.md`, and `docs/BUGS.md` and `docs/LESSONS.md` only through `bugs.mjs`. Code is the implementers'. Never edit a file in `docs/reviews/` and never set `ai-review`: both belong to the reviewer.
- A defect of merged work becomes a bug through `/pitwall:bug`; a defect of the branch in flight is a finding of its review, or a fix within the same change, never a bug (owner, 2026-11-11). On the branch in flight, name a bug that still waits in the git directory in a code span (`` `BUG-<n>` ``): its row reaches `docs/` only with the next branch, and the docs check reads every other `BUG-n` as an ID that must point somewhere.
- Wait for every agent you dispatch: run it in the foreground and read its report before you go on or end your turn. A turn that ends while an implementer or a reviewer runs in the background can end that agent with it, as a headless session showed.
- One change in flight at a time, on its own branch: `epic/E<n>-<slug>`, the epic's file name, or `fix/BUG-<n>` (`loop.branches`). Nothing interrupts it, a blocking bug included: the next change starts from `main` once it is merged.
- When a script hands a step over, show the owner its HANDOFF lines verbatim. Never retry a refused write another way, and never work around a hook: never `git commit --no-verify` or `-n` past the gate before every commit. A commit of nothing but Markdown under `docs/` and `.claude/pitwall.json` passes it even while the gate is red.
- Keep the template's headings and table columns, and write the plain Markdown the docs check reads, as the `plan` skill does.

## Before the loop: stages 0 to 5

The plan is made one stage at a time. Each stage has its own skill, which this one runs, and the owner says yes before the next stage starts.

1. **Find the stage.**
   - No `.claude/pitwall.json` in the folder: stage 0, `kickoff`, with this skill's arguments as the idea.
   - `main` holds a merge commit whose message has `Plan approved by the owner` (`git log --merges --grep="Plan approved by the owner" -1 --format=%H main`): planning is over, go to "Steps" below.
   - Otherwise the `Stage:` line of the session brief names the stage the project stood at when the session started. Once a stage has ended in this session, or when there is no brief (the hooks are off, or the project was laid out in this session), it is the first of `kickoff`, `discovery`, `decide` and `plan` whose docs check does not pass: run `node "${CLAUDE_PLUGIN_ROOT}/scripts/docs-check.mjs" --stage <stage>` in that order. The plan's review and its merge are the second half of the `plan` skill, which resumes there by itself.
   - Stage 0 is over only when a commit holds `.claude/pitwall.json` and the planning branch (`planning.branch`) exists, whatever its docs check says: the brief then says that kickoff is not finished, and without a brief `git cat-file -e HEAD:.claude/pitwall.json` and `git rev-parse --verify -q refs/heads/<planning.branch>` tell. With `.claude/pitwall.json` there and stage 0 not over, an earlier session laid the project out and stopped: the `kickoff` skill resumes it, as its preflight says; never empty the folder and never lay it out again.
   - Between `decide` and `plan` stands the spike, which the brief does not always name. A spike file in `docs/spikes/` with `Outcome: pending`: `spike`, which finishes it. A spike that was not confirmed, with `Follow-up: pending, /pitwall:decide <area>`: `decide`, with that area as its argument. A level whose `spikeRequired` is true (`processLevels`) while the riskiest assumption of `docs/DISCOVERY.md` has no concluded spike: `spike`. A level that makes the spike optional, with no spike in `docs/spikes/` and no plan drafted in `docs/EPICS.md` yet: the owner chooses, a spike on that assumption first or the plan; ask it as one question, unless they answered it in this conversation (step 3 asks it after `decide`).
2. **Run the stage.** Tell the owner in one line which stage starts and what it will ask of them. Read `${CLAUDE_PLUGIN_ROOT}/skills/<stage>/SKILL.md` and follow it from its first step to its Check, as if the owner had run `/pitwall:<stage>`: its rules hold beside the ones above. Claude Code filled two placeholders in this skill's text when it loaded it, and fills neither in a file you read yourself, so fill them as you follow that file: where it names the plugin's folder by a placeholder (a dollar sign, then `CLAUDE_PLUGIN_ROOT` in braces), use the folder two levels above that `SKILL.md`, the one whose `scripts/` and `config/` this skill's commands name; where it names its arguments (a dollar sign, then `ARGUMENTS`), they are what step 1 gave, or empty. Never send a command with either placeholder left in it.
3. **Ask before the next stage.** When the stage's check passes and its commit is made, give its hand-over in a few lines: what it left, and what waits for the owner. Then ask one question: move on to the next stage? Name that stage and say in one line what it does. After `decide`, at a level where the spike is optional, the question offers both ways: a spike on the riskiest assumption first, or the plan. After the plan's merge, the next stage is the epic loop, which starts with E0. Never start the next stage without that yes, and never in the same turn as the hand-over.
   - Yes: go back to step 1 and go on in this session. Once the hooks have warned about the session's call budget (`budgets.sessionToolCalls.warn`), say instead that a fresh session is the better place: "continue" there picks up at the same stage, since the state is in the repository.
   - No, or not now: stop. Nothing is lost.
   - A stage that stops before its check (a preflight that refuses, a command handed over, a question left open) stops this skill too: say what resumes it.

## Steps

1. **Preflight.**
   - Read `.claude/pitwall.json`; without it, or while `main` holds no merge commit whose message has `Plan approved by the owner`, the project is before the loop: follow "Before the loop" above.
   - When `.claude/pitwall.json` has no `autoMerge` (a project laid out before ADR-0010), ask the owner one question: may low and normal risk epics merge without them once `gate` and `ai-review` are green? High risk and bug fixes always wait for them. Record their answer as "The owner's choice of merges" below says, and go on; until it is recorded, every merge waits for the owner, and its allow rules take effect from the next session start. Never write their answer into the docs, an epic or a PR: `.claude/pitwall.json` is its only record, and `merge.mjs` reads it at every merge; where it matters, point to that file (T4a-AC2).
   - When `mergeProtection` is `pending`, tell the owner once and offer to run `node "${CLAUDE_PLUGIN_ROOT}/scripts/protect.mjs"`.
   - The gate before every commit (pitwall's ADR-0012). Run `git ls-files .githooks/pre-commit` and `git config core.hooksPath`. When the hook is listed and the setting is empty, as in a new clone, which does not carry it, run `git config core.hooksPath .githooks`. When the setting names another folder, ask the owner one question: may pitwall's hook replace the hooks they set? On yes, the same command; on no, go on without it. When the hook is not listed, the project was laid out before it, and step 4 lays it out.
   - With a remote, `git fetch origin`. Run `git status --porcelain`: changes that belong to the change in flight stay; anything else the owner commits or drops first. A changed `.claude/pitwall.json` is the owner's answer (`merge-choice.mjs`) or the protection mode (`protect.mjs`): never stash, restore or discard it. Without a change in flight it goes into the first commit of step 4; with one, commit it on that change's branch at once, `git commit -m "chore: record the owner's choice" -- .claude/pitwall.json`, and when the change was already reviewed, a new review round follows, since its head moved. Answers `/pitwall:owner-calls` recorded in an epic's "Open questions" and left in the tree (it never commits on `main` or on a ready PR's branch) stay too, and go into the first commit of the next branch step 4 starts.
2. **Select.** Read `docs/EPICS.md` and the branches (`git branch --list "epic/*" "fix/*" "release/*"`), and run `node "${CLAUDE_PLUGIN_ROOT}/scripts/bugs.mjs" list --json`: the open bugs of `docs/BUGS.md`, of branches not merged yet, and of what waits in the git directory for the next branch.
   - With `gh`, `gh run list --branch main --limit 1 --json conclusion,displayTitle,url`: a last run on `main` that failed is a blocking defect of merged work, since the gate of every PR fails with it. Unless an open bug already names it (found in CI), tell the owner what failed and file it with `/pitwall:bug`, found in CI and blocking; the precedence below then takes it right after the change in flight, and no new change starts while `main` is red.
   - A change is merged when its branch's last commit is the second parent of a merge commit on `main`: pitwall merges with a merge commit (`git log --merges --format=%P origin/main`, or `main` without a remote, lists the parents). A branch with no commit of its own is not merged. Note every merged change whose status in the docs is not yet `merged`, `released` or `fixed`: step 4 records it.
   - A release branch, `release/v<x.y.z>`, not merged is a release in flight: tell the owner that `/pitwall:release` resumes it, and stop. Nothing starts beside it, since its commit records the same changes a new branch's first commit would (ADR-0013).
   - Then by precedence (owner, 2026-11-09 and 2026-11-11):
     1. the change in flight, an `in progress` or `in review` one that is not merged, resumed at its step (its PR, its review round, its merge): nothing interrupts it;
     2. a blocking bug whose fix this step did not find merged, an unconfirmed one included, the oldest first;
     3. the next `planned` epic whose dependencies are all merged;
     4. a bug that is not blocking, the oldest first, once no epic is ready.
   - Nothing left: tell the owner the plan is done, and offer `/pitwall:release`, which they run: it records the changes merged and not recorded yet, the last one of the plan included, and ships them as a version (ADR-0013). Then stop.
   - Tell the owner in a few lines what you picked and why.
3. **Clarify.** Reread the change: the epic and its acceptance criteria (or the bug's row), every ADR it cites, `docs/LESSONS.md` and `CLAUDE.md`. Ask the owner what is unclear or decides something, one question at a time, before any code. Record each answer in the epic's "Open questions" section as a line `Answered (<date>): <the question>: <the answer>`, in place of the question, which `/pitwall:owner-calls` reads (for a bug, in the brief and the PR), except an answer about merges without the owner or about merge protection, which only their own scripts record; a new one-way decision goes through `/pitwall:decide <area>` first. For a bug:
   - an unconfirmed one: first ask the owner to confirm its severity and its class, then `node "${CLAUDE_PLUGIN_ROOT}/scripts/bugs.mjs" set <BUG-n> --severity "<s>" --risk <class>`; when it turns out not blocking, select again;
   - when the owner will not have it fixed: ask what they will do if it comes true, `node "${CLAUDE_PLUGIN_ROOT}/scripts/bugs.mjs" accept <BUG-n>` with their answer on stdin, in a quoted heredoc as `/pitwall:bug` files a bug (`fallback: <their answer>`), and select again.
4. **Branch.**
   - A new branch always starts from `main`: `git switch main`, with a remote `git pull --ff-only origin main`, then `git switch -c <branch>`.
   - A change in flight: `git switch <branch>`, and go to its step.
   The first commit of a new branch starts with `node "${CLAUDE_PLUGIN_ROOT}/scripts/bugs.mjs" flush`: it moves the bugs, risks and lessons that wait in the git directory into `docs/`, and gives a table of `docs/BUGS.md` from before T4b its new columns, each open bug in it blocking and high (tell the owner when it did). Then it records, in `docs/`:
   - each merged change step 2 noted: `merged (#<pr>)` as its status in `docs/EPICS.md`, or for a bug `node "${CLAUDE_PLUGIN_ROOT}/scripts/bugs.mjs" set <BUG-n> --status fixed --fix-pr "#<pr>" --tree`, and an entry in `docs/JOURNAL.md`: what shipped, its review rounds and findings (from its file in `docs/reviews/`), the implementers it took and their calls (from the last "pitwall numbers" comment step 9 left on its PR, `gh pr view <pr> --json comments`; without a remote there is no PR, and the entry says so), and its cost where known;
   - for E0 only, the Approval section of `docs/PLAN-REVIEW.md`: the line `Plan approved by the owner, <date>, at <sha>`, with the date from the plan's merge commit message and the sha of that merge commit (`git log --merges --grep="Plan approved by the owner" -1 --format="%H %B" main`), ADR-0008;
   - this change's status, `in progress`; for a bug, `node "${CLAUDE_PLUGIN_ROOT}/scripts/bugs.mjs" set <BUG-n> --status "in progress" --tree`.
   Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/docs-check.mjs" --stage bug,lesson`; what it reports in the title, the severity, the class, the place it was found, the status or the fix PR of a bug, put right with the owner's answer through `node "${CLAUDE_PLUGIN_ROOT}/scripts/bugs.mjs" set <BUG-n> ... --tree`; anything else (empty steps, expected or actual, a row from before T4b, a lesson with nothing under "Checked by"), ask the owner, who puts it right by hand. What `flush` wrote stays in the git directory until this commit holds it, so a session that ends here loses no new row. When `flush` refuses a table whose columns are not the template's, ask the owner to put the template's columns back by hand, and run it again. Then `git commit -m "docs: start <change>" -- <the files it changed>`, naming each path (`docs/EPICS.md`, `docs/BUGS.md`, `docs/RISKS.md`, `docs/LESSONS.md`, `docs/JOURNAL.md`, `.claude/pitwall.json`, an epic with the owner's answers, ...), never `docs/reviews/`. When step 1 found no `.githooks/pre-commit` in the index, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/layout.mjs" --hook` right after this commit: it commits the template's hook on its own, executable, and sets `core.hooksPath`; a refusal, show the owner verbatim and go on. With a remote, `git push -u origin <branch>`.
5. **Implement.** Dispatch one implementer with the brief below: `pitwall:<riskClasses.<class>.implementer>` with that class's `effort`, by the risk class of the epic or of the bug; for a bug whose cause is unknown, `pitwall:implementer-deep` with the high class's effort, whatever its class. On its report:
   - DONE: go to step 6.
   - PARTIAL: dispatch a fresh implementer with the handoff; the work stays in the tree. A handoff that names only steps for the owner (QA on their laptops, a window to watch) goes to the owner instead: ask them, and go on to step 6.
   - An implementer that stopped without a report (the session ended under it): dispatch a fresh one, with what its commits and the tree show as the handoff; never resume the old one, whose budget is spent.
   - NEEDS_OWNER: ask the owner, one question at a time, record the answers in the epic, and dispatch a fresh implementer with them.
   Every dispatch for this change counts: after `budgets.implementersPerChange` of them, the owner decides whether to go on.
6. **Gate.** Run `bash scripts/gate --full`, once, with the longest timeout (as `/pitwall:gate` does). Red: no PR; dispatch an implementer with the failing output (step 5's count goes on).
7. **PR.** Set the change's status to `in review` in `docs/EPICS.md` (for a bug, `node "${CLAUDE_PLUGIN_ROOT}/scripts/bugs.mjs" set <BUG-n> --status "in review" --tree`), `git commit -m "docs: <change> in review" -- docs/EPICS.md` (or `docs/BUGS.md`), then `git push -u origin <branch>`. When `gh pr list --head <branch> --state open` lists nothing, open it: `gh pr create --base main --head <branch> --title "<E<n> - title, or BUG-<n>: its title>" --body "<body>"`, the body after `.github/pull_request_template.md`: the risk class, each acceptance criterion with what covers it (from the implementer's TESTS), the ADRs, what was not done (SHORT OF), the review file, and, when step 4 ran `layout.mjs --hook`, a line saying that the branch also brings pitwall's gate before every commit, `.githooks/pre-commit`, laid out from the template. A failed push or PR is not retried: show the error, and the reviewer's status step hands it over.
8. **Review.** Dispatch `pitwall:code-reviewer` with the reviewer brief below, a fresh agent each round. Show the owner its STATUS, the open items in a short list, a LESSON it proposes, and any HANDOFF lines verbatim. For each open item:
   - a finding in the code: dispatch a fresh implementer to close the findings by number (step 5's count goes on); it commits on the branch;
   - a risk to accept: ask the owner; on yes, `node "${CLAUDE_PLUGIN_ROOT}/scripts/bugs.mjs" risk --tree` with `risk: <the risk>` and `fallback: <their fallback>` on stdin, in a quoted heredoc, which numbers it past every `R-n` in `docs/RISKS.md`, waiting in the git directory and on every branch, and dates it;
   - a question only the owner can answer: ask it and record the answer where it belongs.
   - a LESSON: ask the owner whether to record it; on yes, follow `/pitwall:lesson`, with `--tree`, so that it lands on this branch where the next implementer of the change reads it;
   - a status the reviewer could not set because Claude Code did not let `review-status.mjs` run (REVIEW STATUS says "not run": a project whose owner keeps every merge for themselves has no allow rule for it): with STATUS APPROVED, hand the owner the command it names, to run themselves in a terminal from the project folder, and stop here: the change is ready to merge once they have, and `/pitwall:continue` resumes at step 9. With CHANGES, hand nothing over: close the findings, and the next round sets the status on the new head.
   Commit the docs you changed by name (`git commit -m "docs: close review round <n> of <change>" -- <paths>`), never the review file, which the reviewer's script commits; push, and run the next round.
   The loop has an end, the same as the plan's (L-8). The first `review.ownerDecidesAtReject` rounds are full reviews. After them, show the owner what is still open, and they decide, item by item, to fix it or accept it as a risk. Later rounds are verification rounds: the reviewer checks its findings, adds only blocking ones, and lists the rest under NOTES, which the owner reads and none of which blocks. Rounds stop at `review.maxRounds` in all: what is open then, the owner fixes or accepts, and the last round only records it.
9. **Merge**, once the reviewer returned APPROVED. First leave the numbers the journal needs on the PR, where the next session reads them: `gh pr comment <pr> --body "pitwall numbers: implementers <n>, their tool calls <list>, review rounds <n>, findings <n> (<n> blocking)"`. Then run exactly `node "${CLAUDE_PLUGIN_ROOT}/scripts/merge.mjs" --change`, with no other argument: the owner's allow rule names it so.
   - Exit 0 (`RESULT: merged`): go to step 10.
   - Exit 4 (`RESULT: waits for the owner`): show the owner one summary (the change, its risk class, the reviewer's verdict and its file, what was not done, what it makes visible in the product and what is not there yet, and the manual QA scenarios that are theirs to run, before their yes or after it) and ask one question: merge it now? A bug fix always waits for this yes, at any class (ADR-0010). On yes, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/merge.mjs" --change --owner-approved`. On no, or not yet, stop here; `/pitwall:continue` resumes at this step.
   - Exit 3: when the gate is still running, run the same command again (a yes still stands); otherwise show the HANDOFF block verbatim and stop.
   - Exit 1: show why it refused; when `ai-review` is not success on the head, run one more review round (step 8); when the gate is red, dispatch an implementer with its failure, as in step 6.
   - Claude Code does not let the command run (a prompt nobody answers, or auto mode's refusal): hand the owner the same command to run themselves in a terminal from the project folder, and stop; the change is ready to merge.
10. **Record and loop.** With a remote, `git switch main` and `git pull --ff-only origin main`. The merge is recorded by the first commit of the next branch (step 4), since `main` is protected. Count the changes merged in this session: after as many as this skill's arguments say, when they give a number, and never more than `budgets.epicsPerSession`, stop and suggest a fresh session; otherwise go back to step 2. When you stop, say in a few lines where each change stands and what waits for the owner.

## The owner's choice of merges

Whether low and normal risk epics merge without the owner is theirs to say and theirs to record (ADR-0010). Once they have answered the question in this conversation, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/merge-choice.mjs" --allow` for yes or `--deny` for no yourself, from the project root, alone in its call. pitwall's guard sends exactly that command to Claude Code's permission prompt, whatever the session's mode or allow rules, and the owner's yes at the prompt is what records the answer as theirs. Tell them, in the message before it, that Claude Code will ask them to allow one command and why.

- Never run it for an answer the owner did not give in this conversation, never add or suggest an allow rule for it, and never try another way when it is refused.
- The owner says no at the prompt: nothing is recorded, and every merge waits for them.
- Claude Code does not ask (nobody is at the prompt, as in a headless session, or the session's mode never asks, and the guard refuses): hand the owner the command to run themselves in a terminal, on one line of its own in a code block, with `--project "<the project root>"` at its end so that it runs from any folder.

## Implementer brief

Only what the implementer needs, never this conversation: the project root; the change (the path of its epic file, or its row of `docs/BUGS.md` quoted) and its branch; its risk class; the paths of the ADRs it cites; the owner's answers from step 3; for an epic, the lines of `docs/PLAN-REVIEW.md` under "Notes for the implementers" that start with its ID, quoted as advice the plan's reviewer left; the task: implement the change, continue from a handoff (quoted), close review findings (the review file's path and the finding numbers), or make the gate green (its failing output quoted); and the config path `${CLAUDE_PLUGIN_ROOT}/config/defaults.json` with its call budget, `budgets.subagentToolCalls`.

## Reviewer brief

Only what the reviewer needs to find the change, never this conversation or the implementer's reports: the project root; the change and its branch; the round number, one more than the `- Round:` of the change's review file on the branch, or 1 when there is none, and from round `review.ownerDecidesAtReject` + 1 on, that it is a verification round; the config path `${CLAUDE_PLUGIN_ROOT}/config/defaults.json`; the template `${CLAUDE_PLUGIN_ROOT}/template/docs/reviews/template.md`; the paths to read (`docs/LESSONS.md`, `CLAUDE.md`, the epic's file or `docs/BUGS.md`, the ADRs it cites, `docs/RISKS.md`, the review file); and the commands it may run, with their paths and the project root spelled out, so it needs no `cd`:

- read-only git: `git diff main...HEAD`, `git log`, `git show`, `git status`, `git rev-parse HEAD`, `git ls-files`, `git blame`;
- `bash scripts/gate --full` (or `--fast`);
- `node "${CLAUDE_PLUGIN_ROOT}/scripts/docs-check.mjs" --root "<project root>" --stage code-review`;
- `node "${CLAUDE_PLUGIN_ROOT}/scripts/review-status.mjs" --review code --state success --project "<project root>"`, or `--state failure --description "code review: <n> open"`.

## Output

- Per change: its branch, its commits, the PR, `docs/reviews/<change>.md` from the reviewer with `ai-review` on the PR, and the merge into `main` with a `feat(E<n>): ...` or `fix(BUG-<n>): ...` merge commit that records the risk class and who approved it.
- In the first commit of the next branch: what waited in the git directory (bugs, risks the owner accepted in place of a fix, lessons), the statuses in `docs/EPICS.md` and `docs/BUGS.md`, an entry per merged change in `docs/JOURNAL.md`, and for E0 the Approval line of the plan.

## Check

Each merged change passed `scripts/gate --full` before its PR and `docs-check --stage code-review` before `ai-review` turned green, and `merge.mjs` merged it only with both checks green on the reviewed head, by its risk class or after the owner's yes. `docs-check --stage bug,lesson` passes on the first commit of each branch.
