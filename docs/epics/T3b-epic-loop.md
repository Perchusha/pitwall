# T3b - The epic loop

Goal: `/pitwall:continue` takes a project from a merged plan through its epics and bug fixes, each to a merged PR, and needs the owner only where the process asks for them.
Depends on: T3a
Risk class: high (merges by risk class, and the rules that let a merge run without the owner)
ADR: ADR-0002, ADR-0005, ADR-0007, ADR-0008, ADR-0010, ADR-0011

## Acceptance criteria

- [ ] T3b-AC1: Conductor. `/pitwall:continue` orients from the session brief (T3a-AC2), git and `docs/BUGS.md`, and selects by precedence: an open bug, then the change in flight (an `epic/*` or `fix/*` branch, its PR open, or merged and not yet recorded), then the next planned epic whose dependencies are merged. Before any code it rereads the epic or the bug, its acceptance criteria and its ADRs, and asks the owner what is unclear, one question at a time. The first commit of each new branch records what merged since the last one; the first commit of E0's branch also writes `Plan approved by the owner, <date>, at <sha>`, with the sha of the plan's merge commit, into the Approval section of `docs/PLAN-REVIEW.md` (ADR-0008). After `budgets.epicsPerSession` merged changes it stops and suggests a fresh session.
- [ ] T3b-AC2: Implementers. One implementer works on one change, picked by its risk class (`riskClasses.<class>.implementer`, dispatched at that class's `effort`), on `epic/E<n>-<slug>` or on the branch of a bug fix, following the `epic` skill: tests for every new module, a test or a QA scenario for every acceptance criterion, `scripts/gate --fast` while it works, within its call budget (T3a-AC5). It returns DONE, PARTIAL or NEEDS_OWNER. A PARTIAL report gets a fresh implementer with the handoff, and the work stays in the tree; a NEEDS_OWNER question goes to the owner, one at a time. Its check before stopping runs at its handback (T3a-AC6).
- [ ] T3b-AC3: Gate and PR. `scripts/gate --full` runs before the PR, and a red gate opens no PR. The PR lists each acceptance criterion with what covers it, the ADR links, what was not done and the review file. `/pitwall:gate` runs the gate with one bounded wait and reports PASS or FAIL with the failing steps.
- [ ] T3b-AC4: Code review (ADR-0007, ADR-0011). The `code-reviewer` agent, a fresh sub-agent in the local session every round, briefed with paths only, reads `docs/LESSONS.md` first, then the change, its acceptance criteria, its ADRs and its diff against `main`, and writes only the change's review file: `docs/reviews/E<n>-<slug>.md` for an epic, `docs/reviews/BUG-<n>.md` for a bug fix. The file records the commit it reviewed, what covers each acceptance criterion, and numbered findings, each closed by a commit or by a risk the owner accepted. The review rule of the plan applies: `review.findings`, `review.ownerDecidesAtReject` and `review.maxRounds` (L-8). `docs-check --stage code-review` passes only when every criterion is covered and every finding is closed. `review-status.mjs --review code` sets `success` only when that check passes and the commits after the reviewed one changed nothing but the review file; otherwise it sets `failure`, or a new round runs. The guard of T3a-AC4 gains the code reviewer's row in `hooks.agents`.
- [ ] T3b-AC5: Merge by risk class through `merge.mjs` (T2). The PR of an epic or a bug fix merges only when `gate` and `ai-review` are green on its head. Low and normal merge without the owner when the project's owner allowed it (ADR-0010) and after the owner's yes otherwise; high always waits for the owner's yes.
- [ ] T3b-AC6: The owner's choice of ADR-0010. One question at kickoff, or at the first `/pitwall:continue` of a project laid out before it. The answer is recorded in `.claude/pitwall.json` by a script the owner runs in a terminal: the session hands it over (L-6), and the guard of T3a-AC3 refuses it to every agent. On yes the script writes the two narrow allow rules into `.claude/settings.local.json`, only when the review guard of T3a-AC4 is installed; they are written again when the plugin's path changes, and removed on no.
- [ ] T3b-AC7: Skill runs. `node scripts/e2e.mjs` runs the epic loop of the lite system headless against a fake GitHub: a local bare repository as `origin`, PRs, commit statuses, a CI that runs `scripts/gate --full` on each PR head as the check `gate`, and merges. By default it runs E1 from the state E0 saved; the run from E0 goes before the PR. Each stage writes its numbers as soon as it ends. `--github` runs the same against an empty private repository the owner created, where the session only pushes and opens PRs and merge protection is `local-hook`; it records the API's answers, and `scripts/check.mjs` checks the fake against them.
- [ ] T3b-AC8: Tests. `scripts/check.mjs` runs `review-status.mjs --review code`, `merge.mjs` on epic and fix PRs by risk class and the owner's choice, and the script of AC6 against the fake `gh`; `docs-check --stage code-review` on reviews the way the reviewer leaves them and on each kind of gap; and the hooks on payloads recorded from the code reviewer and an implementer, with the false refusals of L-9 counted as failures.

## Decisions

One-way, asked one at a time (2026-11-09):

- Code review findings live in a file per reviewed change, named after it: `docs/reviews/E<n>-<slug>.md` or `docs/reviews/BUG-<n>.md` (owner's edit), and `review-status.mjs` sets `success` only when nothing but the review file changed after the reviewed commit (owner's edit, ADR-0011).
- The headless run uses both: a fake GitHub by default, and once before the PR an empty private repository on GitHub. The owner creates and deletes that repository, and the session only pushes and opens PRs, so it needs neither `delete_repo` nor the right to create repositories; it is private because in the mode `local-hook` GitHub does not back pitwall's protection, so checking it against the real API matters more (owner's edit). The `--github` run records the API's answers, as T3a recorded the hook payloads, and `scripts/check.mjs` checks the fake against them, so the fake is checked against real data and not against pitwall's model of GitHub (owner's edit). A run costs about $50 to $150, so by default the fake run starts from the state E0 saved, the full run from E0 goes before the PR, and every stage writes its cost as soon as it ends, as in T1 (owner's edit).

Two-way, picked by the agent and accepted by the owner as a list on 2026-11-09, with the owner's edits (marked):

| Area | Choice | Why, in one line |
| --- | --- | --- |
| Review file | The lines `Change:` and `Reviewed: <full sha>`; `## Acceptance criteria`, each criterion with the test or QA scenario that covers it; `## Findings`, numbered, with `file:line`, a severity (`blocking` or `should fix`) and a last cell that starts with the sha of the branch commit that closes it, an accepted `R-n`, or `open:`; nits go under NOTES in the report; the plain Markdown grammar of `docs/PLAN-REVIEW.md` (L-7); the template adds `docs/reviews/README.md` and `template.md` | "Every criterion covered, every finding closed" is checked by a script |
| Reviewed commit | The reviewer writes `git rev-parse HEAD` at the start of its round; `review-status.mjs` refuses success when that sha is not an ancestor of the head or `git diff --name-only <sha> HEAD` lists anything but the review file; the plan review keeps its rule | The plan's check reads the tree it commits; code can change between rounds |
| Code reviewer | Read, Grep, Glob, Write, Edit and Bash; writes only `docs/reviews/*.md`; one command per call with no `;`, `&`, `\|`, `<`, `>`, backtick, `$(` or line break: read-only git (`diff`, `log`, `show`, `status`, `rev-parse`, `ls-files`, `blame`), `scripts/gate` in any mode, `docs-check.mjs` and `review-status.mjs` | It reads the diff and runs the tests itself, and writes nothing else |
| Closing findings | A fresh implementer with the review file as its brief; the main conversation edits only docs: the epic, `docs/RISKS.md` for an accepted risk, the owner's answers | Only implementers write code, under their checks before stopping |
| Bug fixes | Branch `fix/BUG-<n>`, the same loop; `implementer-deep` when the cause is unknown, `implementer` otherwise; merged only after the owner's yes until T4 gives bugs a risk class; the checks after edits and before stopping run on `fix/*` too (`loop.branches`) | A new column in `docs/BUGS.md` changes a template table, which T4 owns |
| Merge method | A merge commit, with `--match-head-commit`. Its message is conventional: `feat(E<n>): <title> (#<pr>)` for an epic, `fix(BUG-<n>): <title> (#<pr>)` for a fix, with the risk class and who approved in the body (owner's edit) | As the plan (ADR-0008): the reviewed commit stays reachable from `main`, `--first-parent` shows one commit per change, and "merged" reads from git without GitHub |
| Recording | What merged since the last branch is recorded by the first commit of the next one: `merged (#n)` in `docs/EPICS.md`, `fixed (#n)` in `docs/BUGS.md`, an entry in `docs/JOURNAL.md` with the numbers (implementer runs and calls, review rounds and findings), which wait in a comment on the change's PR until then (T3b review); `in progress` and `in review` are committed on the change's own branch | `main` is protected; pitwall itself works this way |
| Selection | A red last CI run on `main` stops the conductor and goes to the owner; then any open bug before the next epic until T4 (owner's edit); then the change in flight; then the next planned epic whose dependencies are merged; one change in flight at a time | SPEC 6 puts a fix first; parallel epics collide in the docs |
| PARTIAL | A fresh implementer with the handoff, a new `agent_id` with a new budget; at most `budgets.implementersPerChange` (3) per change, then the owner decides | SendMessage would bring back the same agent with its budget used up |
| Effort | The conductor passes `riskClasses.<class>.effort` at each dispatch, which the Agent tool takes since 2.1.292; no `effort` in the agents' frontmatter; the implementers preload the `epic` skill through `skills:` | One source for the effort; plugin agents take `skills` but ignore `hooks` and `permissionMode` |
| The owner's choice | `"autoMerge": false` in the template's `.claude/pitwall.json`; no key in an older project means "not asked yet" and works as false; `scripts/merge-choice.mjs --allow` or `--deny`, run by the owner in a terminal, refuses to run under Claude Code (`CLAUDECODE=1`), the guard refuses it to every agent, and it writes the rules only after it checks that the guard is installed and refuses `review-status.mjs` to the main conversation | ADR-0010, with the yes out of every agent's reach |
| Allow rules | `review-status.mjs` with a wildcard for its arguments; for merges only the exact command `merge.mjs --change`, with no wildcard, so `--owner-approved` never rides on a rule: high risk and the owner's yes go through the classifier or a prompt; the exact spelling (quotes, Windows paths) is probed in the build | Narrower than ADR-0010 allows |
| Refreshing the rules | The SessionStart hook writes the rules again when `.claude/pitwall.json` says yes and the plugin's path has changed, and removes them on no; the brief says so; Claude Code reloads settings files in a running session | A plugin update needs no new command from the owner; the hook is pitwall code, not an agent |
| Kickoff question | The last question, after merge protection; no needs nothing (the template says false), yes hands over the command; in an older project `/pitwall:continue` asks once and hands over the command for either answer, `--deny` recording false so the question is not asked again | ADR-0010's one question, and no question twice |
| Helpers | `/pitwall:gate` is built here; `/pitwall:owner-calls` moves to T4 with bug, lesson and release | T3b is the loop; the conductor names what waits for the owner when it stops |
| pitwall's own repository | Not laid out as a pitwall project: with `--plugin-dir plugins/pitwall` the guard would refuse every edit of the plugin, a switch of the guards, and the gate after every edit would be `check.mjs`; its merges wait for the owner (ADR-0010); revisit after T5 | The hooks would stop the work they guard |
| Headless run | Stages `kickoff, discovery, decide, spike, plan, e0, e1`: no flags runs e1 from the saved e0, `--from e0 --until e1` before the PR, `--until plan` the planning stages; `scripts/fake-gh.mjs` grows into the fake GitHub for both `check.mjs` and the run, on the session's PATH as `gh`, answering as a private repository on GitHub Free (`local-hook`), with a CI that runs `bash scripts/gate --full` in a clean worktree of each PR head once; the scripted owner says no to the ADR-0010 question and yes to E0's merge, and before e1 the harness, as the owner, runs `--allow`, so E1 merges by itself; the run's allow list leaves out `review-status.mjs` and `merge.mjs`; `--github <owner>/<repo>` first checks that the repository is empty and private, and records the answers in `scripts/github-responses/` without tokens or personal paths | Both merge paths, through the same rules and classifier as a real project |
| Version | 0.5.0 | New skills, agents, scripts, a template folder and a key are additions (ADR-0006) |

## Out of scope

- Releases, QA, filing bugs and lessons, and `/pitwall:owner-calls` (T4); here the loop stops after the merge and records it.
- Adopting an existing project (T6).
