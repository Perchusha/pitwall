# T4c - Releases and a minimal QA

Goal: the merged changes of a pitwall project ship as a version with a changelog and a local build, checked by a qa agent against every closed epic's criteria, and tagged by the owner after their yes; the manual QA left to the owner comes as a checklist, and defects found go in as bugs.
Depends on: T4d
Risk class: high (tags: a mistake reaches users, and a pushed tag is not taken back quietly)
ADR: ADR-0006, ADR-0007, ADR-0010, ADR-0013

## Acceptance criteria

- [ ] T4c-AC1: Version and changelog. A plugin script, `release.mjs`, reads the first-parent history of `main` since the last release, the highest tag `v<x.y.z>` or a release merged and not tagged yet, and keeps only the merge commits of the loop, `feat(E<n>): <title> (#<pr>)` and `fix(BUG-<n>): <title> (#<pr>)`: the plan's merge, the kickoff commit, earlier releases and any other commit never reach the changelog, and a commit on `main` that is no merge is named to the owner (owner, 2026-11-09). The next version: an epic in it makes a minor, fixes alone a patch, and a major only when the owner names the version. The first release of a project asks the owner one question, 0.1.0 or 1.0.0 (owner's edit). `CHANGELOG.md` at the project root gains a section `## v<x.y.z> - <date>` with `### Added`, one line per epic `E<n>: <title> (#<pr>)`, and `### Fixed`, one per bug; with nothing to release, the script says so and stops (owner, 2026-11-12).
- [ ] T4c-AC3: The release is a change of its own: a branch `release/v<x.y.z>` from `main` with one commit, which adds the changelog's section, sets `released (v<x.y.z>)` as the status of each epic in it, and records each merged change not yet recorded as the first commit of a loop branch does (statuses, journal entries), so the last change of a plan is recorded too (T3b review). It takes no row waiting in the git directory, so a release that stops leaves nothing behind (R-4, item 1). Then the PR, the gate, the qa agent's review (AC5), and the merge, always after the owner's yes, whatever the risk classes of what it holds, with a merge commit `release: v<x.y.z> (#<pr>)` (owner, 2026-11-12).
- [ ] T4c-AC4: The local build. The template gives a project `scripts/build <version>`, a contract like `scripts/gate`: it builds what the owner runs or installs from the tree as it is, may stamp the version into what it builds, changes no tracked file, exits non-zero when it fails and prints one `ARTIFACT: <path>` line for each thing it built. The template's stub fails until E0 fills it in, as E0-AC4 now says. The qa agent runs it on the release PR's head through `release.mjs --build`, which checks each artifact and that the tree stays clean. At every level until T8 the release is this local build; staging and production are T8's. A project laid out before 0.9.0 has no `scripts/build`: the release stops and says so (owner, 2026-11-12).
- [ ] T4c-AC5: The minimal qa agent is the release's reviewer (owner, 2026-11-12). Fresh, briefed with paths only, on the release PR's head, it runs `release.mjs --check` (the changelog and the records match the merges, the branch changes only `CHANGELOG.md` and `docs/`, and no blocking bug is open), the build of AC4 and `scripts/gate --full`; then, for each acceptance criterion of each merged or released epic and for each fixed bug, it reads what the change's review file says covers it: a test whose file is still in the tree passes with the gate, a QA scenario becomes an item of the owner's checklist, and anything else fails. It writes only `docs/reviews/release-v<x.y.z>.md` (the review template: a row per criterion, a finding per failure), files a bug for each failure with `/pitwall:bug`, unconfirmed and so blocking until the owner confirms it (T4b), and sets `ai-review`, success only with no failure. Its `ai-review` means that the automated part passed; the manual checklist is the owner's, and the release merges only after their yes (owner's edit). A red release is closed, its bugs go first, and the release runs again after them.
- [ ] T4c-AC6: No release while a blocking bug is open, one the qa agent has just filed included (owner's edit): `release.mjs` refuses to start one and its check fails, the release's review cannot pass, and `merge.mjs` refuses to merge one.
- [ ] T4c-AC7: The tag and the build are the owner's to publish (owner's edit). After the merge, `release.mjs --tag` hands the owner the commands, as pitwall's own releases are handed to them: `git tag -a v<x.y.z> <the release's merge commit> -F <the changelog's section>`, `git push origin v<x.y.z>`, and `gh release create v<x.y.z> <the artifacts> --notes-file <the same section>`; the artifacts stay local in T4c. It refuses when the tag exists, and when the code of the merge commit differs from the code the qa agent built. No agent creates or pushes a tag; `/pitwall:owner-calls` lists a release merged and not tagged, and no new release starts until it is tagged.
- [ ] T4c-AC8: Where it runs. `/pitwall:release`, built, runs a release when the owner asks; `/pitwall:continue` offers it once the plan is done, and treats an open release branch as the change in flight, which `/pitwall:release` resumes; the owner gets the qa agent's checklist with the one question that merges the release; `/pitwall:owner-calls` lists a release that waits for that yes. SPEC 6 step 8 and SPEC 9's contract name `scripts/build` and `CHANGELOG.md`; ADR-0013 records the release, the options it was chosen over and its limits; ADR-0007 gains the qa agent, for a release only, with its line of the hooks' guard, and the PR names both apart from the rest (owner's edit).
- [ ] T4c-AC9: Tests. `scripts/check.mjs` runs `release.mjs` on scratch repositories (a first release, a minor and a patch, the owner's major, the commits it leaves out, a release merged and not tagged, a tag that exists, a blocking bug open, a build that fails, dirties the tree or names no artifact), `merge.mjs` and `review-status.mjs` on a release branch, `docs-check --stage release` on a release's review, the template's build stub, and the hooks' cases for the qa agent. `scripts/e2e.mjs` gains a loop stage `release` from the state `bug` saved, given a `scripts/build` by the harness as the owner would add it: the release merged with `release: v0.1.0 (#<pr>)` after the owner was asked, `CHANGELOG.md` on `main` with E0, E1 and BUG-1, the release's review file, no tag made by the session, and the tag the harness then makes from the handed commands on the release's merge commit.

## Decisions

One-way (2026-11-10): split out of T4 (see T4a-guards-and-process.md), high risk (owner). If T4c turns out as large as T3b when it starts, it is split again: releases (AC1 to AC3) and QA (AC4, AC5) (owner).

One-way (2026-11-12): made smaller before T5 (owner). Kept: AC1, AC3, the lite level's local build of AC4 and a minimal qa agent of AC5. Moved to T8, after T5: serving pitwall by tag with its ADR (drafted here as the second criterion, now T8-AC1), staging by type of application, and the qa agent's pass in a browser. T5 holds no web application, and Last Ones Down reaches Steam its own way. The criteria keep their numbers, so what the journal and the reviews call T4c-AC3 stays the same criterion.

T4c-AC3 belongs here and not in T4a: recording needs a commit on protected `main`, which only a reviewed PR brings, and the release already makes one (its changelog and version). In T4a the record would need a docs-only PR of its own, with its own branch kind, gate and review, for the same commit the release makes anyway.

One-way, proposed by the agent and accepted by the owner (2026-11-12), recorded in ADR-0013:
- The build command is `scripts/build <version>`, a contract path of ADR-0006 (owner: yes).
- The changelog is `CHANGELOG.md` at the project root, and a version is an annotated tag `v<x.y.z>` whose message is its section; the project's manifests stay the stack's (owner: yes).
- The qa agent reviews the release and sets its `ai-review`, a third agent of ADR-0007, for a release only (owner: yes, on three conditions: its `ai-review` means the automated part passed, the manual checklist is the owner's and the release merges after their yes; no release while a blocking bug is open, one the qa agent has just filed included; the change of ADR-0007 and of the guard's line for `review-status.mjs` named apart in the PR).

Two-way, picked by the agent and accepted by the owner as a list on 2026-11-12, with the owner's additions (marked):

| Area | Choice | Why, in one line |
| --- | --- | --- |
| When | When the owner runs `/pitwall:release`, and offered by `continue` once the plan is done; not after every merge | At the lite level, with 1 to 3 epics, a release per epic adds a PR and a QA run per epic for one user; QA after every merge belongs to staging (T8) |
| Version | An epic makes a minor, fixes alone a patch, a major only by the owner's word; the first release asks the owner 0.1.0 or 1.0.0 (owner's addition) | SPEC's rule; the owner decides when 1.0 ships |
| Changelog | Keep a Changelog's headings (`### Added`, `### Fixed`), one line per merge from its subject; written by `release.mjs`, never by hand | Read by people and tools alike; the merge commit's subject is already the change's title |
| Tag | Annotated, `v<x.y.z>`, on the release's merge commit, its message the changelog's section; made and pushed by the owner from the commands `release.mjs --tag` hands over, as in pitwall itself (owner's addition) | The tagged tree holds its own changelog; a pushed tag is not taken back quietly |
| Artifacts | Local in T4c; the release hands the owner `gh release create v<x.y.z> <artifacts>` (owner's addition) | Publishing them is the owner's step, and staging is T8's |
| Release branch | `release/v<x.y.z>`, a third kind in `loop.branches`; its first commit flushes nothing | A release that stops must leave no row only an abandoned branch holds (R-4, item 1) |
| Build | Run by the qa agent on the PR's head through `release.mjs --build`, not by the conductor; the release's commit changes only docs, so the tag holds the built code | One place for the build and its check; `release.mjs --tag` refuses when the tagged code differs from the built code |
| QA scope | Every criterion of every closed epic, and every fixed bug's regression test, through the review files' "Covered by" | The review files already map each criterion to its test or QA scenario |
| A red release | Closed and started again after the fixes, not kept open | Its version and changelog would change with the fixes anyway |
| Older projects | No `scripts/build`: the release stops and says so; no `CHANGELOG.md`: `release.mjs` creates it | One missing file the owner adds once, and nothing laid out behind their back |
| Out of scope | Uploaded artifacts, staging, production and its smoke check, a browser pass, pitwall's own releases (T8) | The owner's smaller T4c |
| Runs before the PR | `scripts/check.mjs`; `e2e --hooks` (about $1), since the qa agent runs `review-status.mjs`; the new loop stage `release` from the state `bug` saved (estimate $10 to $15) | The runs that cross what changes |
| Version | 0.9.0 | A built skill, a built agent, a script and two template files are additions |
| Size | About 1.5 to 2 thousand lines over 40 to 50 files: 1.2 to 1.5 times T4b, about half of T3b; not split | Below the owner's threshold for a split; and with the qa agent as the release's reviewer, a release without QA would need a review of its own |

## Out of scope

- The guards and the loop's follow-ups (T4a); bugs and lessons (T4b); the gate before every commit (T4d).
- Serving pitwall by tag, staging by type of application, QA in a browser, uploading the artifacts (T8).
